# 流程设计

当收到 flow 设计或优化请求时，根据需求生成完整的 flow.md 文件。

## 输入

从请求中获取：

**创建模式**：
- **flow 名称**：英文短横线格式
- **用途描述**：解决什么问题
- **需要的工具**：执行时用到的内置工具列表
- **需要的 providers**：外部 API 依赖（可选，如 kling、openai）

**优化模式**：
- **flow 名称**：要优化的流程名
- **现有 flow.md 内容**：当前流程的完整内容
- **优化建议**：从对话中发现的问题和改进方向
- **对话摘要**：触发优化的对话上下文

## 输出格式

返回完整的 flow.md 内容，严格遵循以下格式：

```markdown
---
name: {flow-name}
tools: []
version: 1
---

# {流程标题}

{流程 prompt 正文，核心流程 < 2000 字}

## 流程

### 1. {步骤1标题}
{具体操作步骤}

### 2. {步骤2标题}
{具体操作步骤}

## 重要原则
- {原则1}
- {原则2}
```

如果流程需要详细参考文档、触发示例或可执行脚本，可以额外指定子目录：
- `references/` — 详细参考文档，flow 激活时按需注入
- `examples/` — 触发示例，帮助 agent 判断何时使用此 flow
- `scripts/` — 可执行脚本

## 设计原则

1. **description 必须具体**：写用途不写触发条件，50字以内
2. **tools 最小化**：只声明非 core 工具（MCP + file_write 等），core 工具自动加载
3. **providers 声明**：如果 flow 需要调用外部 API，在 `requirements` 部分添加：
   ```markdown
   ## Requirements
   - providers: ["{provider_name}"]
   ```
   这样运行时系统会自动注入对应的 API 密钥到环境变量
4. **步骤可操作**：每一步都要明确做什么、用什么工具、传什么参数
5. **边界清晰**：说明 flow 不做什么，避免过度执行
6. **正文精简**：核心流程控制在 2000 字以内，详细内容放 references/

## 优化模式原则

1. **保留有效的部分**：不要重写整个流程，只改需要优化的部分
2. **分析失败原因**：从对话摘要中定位流程流程的不足之处
3. **增量改进**：每次优化只解决一个明确的问题
4. **向后兼容**：优化后的流程不应破坏已有的工作流

## 返回

直接返回完整的 flow.md 内容，不要附加解释。clone-trainer 会将它写入目标分身的 `flows/{flow-name}/flow.md`。
