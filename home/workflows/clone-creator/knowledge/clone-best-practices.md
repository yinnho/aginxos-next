# 分身设计最佳实践

## 命名规范

- 使用英文小写 + 短横线：`customer-support`、`sales-bot`、`tech-writer`
- 名字要有意义，一看就知道分身做什么
- 避免过长的名字，控制在 3-4 个词以内

## 人格设计 (SOUL.md)

- **身份**：一句话说清楚"我是谁"
- **性格**：2-3 个关键词描述（专业、友好、简洁...）
- **风格**：明确沟通偏好（用中文/英文、正式/随意）
- **边界**：说明哪些事情不做（如不提供医疗建议）

## 系统指令 (system_prompt.md) 写法

好的系统指令结构：
1. **角色定位** — 明确身份和能力范围
2. **工作流程** — 按步骤描述处理逻辑
3. **行为约束** — 该做什么、不该做什么
4. **输出格式** — 期望的回复格式

### 反模式（避免）
- ❌ 过于笼统："你是一个有用的助手"
- ❌ 过于冗长：超过 2000 字的系统指令
- ❌ 矛盾的指令："要详细但要简洁"

### 好的模式
- ✅ 具体场景："当用户询问退货政策时，先确认订单号，然后查询退货规则"
- ✅ 条件分支："如果是 VIP 用户，走快速通道；普通用户走标准流程"
- ✅ 输出示例：给出期望的回复格式示例

## 流程设计

### description 写法（flow frontmatter）
- 非空必填——空 description 的 flow 不会被系统注入，声明的工具全部失效
- 写用途和触发场景，不要过于宽泛
- ❌ "当需要时使用" / ❌ "xxx 技能"（废描述）
- ✅ "当用户询问订单状态或物流信息时使用"
- ✅ "当用户表达购买意向或询价时使用"

### 流程粒度
- 一个流程对应一个完整的业务流程
- 不要把所有功能塞进一个流程
- 也不要把一个简单操作拆成多个流程
- 通常 3-7 个流程是合适的范围

### allowed_tools
- 只列出该流程**额外**需要的工具（基础工具已默认包含，不需要声明）
- **默认已包含的自进化工具**：`knowledge_add`、`knowledge_list`、`knowledge_read`、`knowledge_lint`、`file_read`、`file_write`、`file_list`、`memory_store`、`memory_recall`、`user_profile`
- 需要额外声明的工具：`web_fetch`、`web_search`、`shell_exec`、`browser_*`、`agent_*` 等专业工具

## 知识文件

- 按主题拆分，每个文件聚焦一个领域
- 使用清晰的 Markdown 结构（标题、列表、表格）
- 知识文件不是系统指令 — 只放事实性内容
- FAQ 格式很适合问答类知识

## 典型分身类型参考

### 客服分身
- 流程：FAQ 回答、工单创建、退货处理
- 知识：产品信息、退货政策、配送说明
- 人格：耐心、专业、以解决问题为导向

### 销售分身
- 流程：产品推荐、报价生成、预约安排
- 知识：产品目录、定价策略、竞品分析
- 人格：热情、主动、善干倾听需求

### 研究分身
- 流程：文献搜索、数据分析、报告生成
- 知识：研究方法、领域术语、数据源
- 人格：严谨、深度思考、注重证据

## 插件驱动的分身

### 概念

插件（plugin）为分身提供了连接外部平台的能力。分身通过 `allowed_tools` 引用插件工具，通过 `template.json` 的 `plugins` 字段声明插件依赖。

详见 [plugin-tools](plugin-tools.md)。

### 机器人创建分身

专门帮助用户在特定平台上创建机器人，并把创建好的机器人绑定到用户已有的分身。

- `plugins: ["wecom"]`（或 "feishu"、"dingtalk"）
- 流程：引导用户完成平台创建流程（如 QR 扫码）、调用平台 API、注册机器人到 plugin.toml、绑定到目标分身
- 知识：目标平台的机器人创建流程、API 调用方式、plugin.toml 格式
- 人格：专业、引导性强、步骤清晰
- 不需要子代理（单角色即可完成）

### 企业协作分身

使用企业微信/飞书的工具完成日常协作任务。

- `plugins: ["wecom"]` 或 `["feishu"]`
- 流程：消息管理、文档协作、日程安排、会议管理
- 知识：平台操作流程、最佳实践
- 可以结合业务知识（如产品信息、客户数据）

### 公众对话分身

蒸馏公众人物的思维方式，让用户能和"他"对话（如马斯克、刘震云）。

- 核心文件：SOUL（视角+风格+内在张力+禁忌）+ system_prompt（身份锚定+回应规则+诚实边界）+ 一个主 flow + 6-8 个 references
- 关键方法：6维研究 → 三重验证提取心智模型 → 捕捉内在张力 → 量化表达DNA
- 流程结构：`flows/<name>-voice/flow.md` + `references/`（含必选的 iconic-quotes.md）
- 进化策略：`aggressive`（公众分身需要广泛积累知识）
- 不需要子代理（单角色即可），不需要 knowledge/ 目录（知识集中在 flow references 中）
- 禁忌：绝不编造语录、绝不以第三人称说话、不懂的话题直接说不懂
- 必选项：内在张力（至少2个）、诚实边界（信息不足领域+调研截止日期）
- 详见 `knowledge/celebrity-distillation.md`

### 人格对话分身（新增）

基于用户提供的私有数据（聊天记录、日记、社交媒体），克隆真实个体（用户自己、好友、前任等）。

- 核心文件：SOUL（视角+风格+内在张力+禁忌）+ PERSONALITY-PROFILE（人格提取报告）+ EXPRESSION-DNA + 一个主 flow + relationship-context.md
- 关键方法：数据预处理 → 统计提取人格特征 → 表达DNA量化 → 内在张力推断
- 流程结构：`flows/<name>-voice/flow.md` + `references/`（含必选的 iconic-moments.md、relationship-context.md）
- 进化策略：**`conservative`（人格层冻结，只允许知识层补充事实）**
- 需要 `personality-extractor` 子代理执行人格提取
- 禁忌：不输出原始对话内容、不做心理诊断、不推断敏感个人信息
- 必选项：授权声明、AI身份声明、情感边界、删除机制、第三方 consent（如适用）
- 详见 `knowledge/personality-extraction.md` 和 `knowledge/personality-ethics.md`
